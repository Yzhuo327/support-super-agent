# 物流跟进首版实现说明

## 目标与边界

首版实现客户显式创建物流工单、工作人员提交模拟事件、系统继续处理同一工单的闭环。用户已授权跑通后发布到自己的 GitHub，后续在同一仓库更新。

上游为 `nitanandsinghupw/langgraph-support-agent`，基线提交为 `b6fe9faebff8a1af549ae7b8cabcb0b6e6479cec`。上游 Git 历史与 MIT 许可证保留。

## 实际取舍

复用 `graph.py::build_graph()` 与 `tools.py::make_tools()`，在 `tickets.py::FollowupService` 内只注册 `track_shipment`。首版不接入 DSH 运行时，不拆分多个 Agent。工单创建即提供固定物流跟进授权；尚未实现通用授权规则引擎。

事件只提供固定结构的状态及序号，不允许附带指令或客户身份。客户身份来自 API 边界，物流模拟事件需要工作人员密钥。客户撤销或工单完成后，后续事件只记录为忽略。

SQLite 在事件处理期间保持写事务，将事件、工单更新与本地通知一起提交。模型执行只有只读工具，因此执行失败回滚后可以安全重试本地状态提交。代价是慢模型会延长数据库写锁；真实高并发部署需要另行设计任务领取、租约及事务外执行，不能直接沿用这个演示结构。

通知采用国际化模板，内容来自模型成功调用物流工具后的核验结果，不直接采用模型自由生成的文本。跟进事件的数据视图与原项目的订单、支付内存存储分离，避免将模拟状态变化误称为实际订单更新。未来统一订单存储时应消除此限制。

观察模式只记录事件的候选决策，不执行模型、不推进工单。切换为自动模式后，已经观察过的相同事件仍保持原始结果，需提交新的事件标识；序号须高于工单已执行的序号。

## 验证说明

新行为先添加接口契约测试，确认因缺少 `followup_mode` 失败后再实现。新增用例包括正常推进、重启恢复、重复事件、乱序事件、相同状态抑制通知、越权访问、撤销、终态、非法输入、模型越界调用、失败重试及两个服务实例并发处理。

Windows 沙箱内 FastAPI TestClient 曾阻塞。线程栈显示 Python asyncio 在创建本地 socket 时阻塞，随后在允许本地网络的环境中执行测试。此问题不通过修改业务代码绕过。

`python -m support_agent.demo` 通过真实 FastAPI 路由运行演示，并重新创建服务实例、重新打开 SQLite 数据库；这项演示本身不等同于独立操作系统进程重启测试，也不涉及真实模型或外部通知渠道。

此外，通过独立启动本地 uvicorn、创建工单、终止服务进程、确认原服务停止响应、启动新进程并提交重复物流事件，实际验证了进程重启恢复。最终工单状态为 `completed`，两次状态变化仅生成两条通知。Windows 临时文件清理曾遇到文件占用，因此验证脚本保留在被忽略的 `.tmp` 中，保留证据而不将其纳入产品。

代码检查发现模型工具参数错误时，ToolNode 可能返回非 JSON 错误文本。补充失败测试后，执行器忽略无效证据，统一返回可重试的 502，且不提交事件或通知。
